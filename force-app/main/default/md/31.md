## ■4.入力チェック

### チェックの前提

1. 対象ファイル：登録対象（従事事業～従事事業実績）ごとに 1 ファイル。チェックありの登録対象のみ対象とする。以下の見出しは登録対象。
2. 用語
　・取込データ：今回取り込む対象ファイルの全行
　・既存データ：正式オブジェクト（従事事業～従事事業実績、マスタ）の登録済みレコード
　・事業キー：従事事業No.＋従事場所No.＋実施年度
　・取込ユーザ：登録ボタンを押したユーザ。ユーザ種別・支部コードは共通部品 Juj_CommonController.getLoginUserInfo から取得する（ファイル内チェック用に画面の初期表示時に取得し、整合性チェックでは Apex で取得し直す）。
　　システム管理者 → スーパーユーザ、ユーザー区分 1 → 支部連、2 → 支部、それ以外（0・空）→ 事務局。事務局ユーザの支部コードは本会（000）、支部ユーザは所属支部の支部コード【要確認 C-5・D-31】
　・事務局ユーザ：スーパーユーザ、事務局のユーザ／支部ユーザ：支部、支部連のユーザ
　・従事者：[会員] または [相談員マスタ]
3. 判定ルール
　・親レコード：既存データ または 取込データ にあれば存在とする。
　・実施年度内：実施年度の 4月1日 ≦ 日付 ≦ 翌年 3月31日
　・従事事業の応募時入力項目フラグが空白の場合：既存は 必須＝省略可・任意＝許可【要確認 D-43】、取込は登録時の省略値（必須＝省略可・任意＝禁止。「32」(3)②-1）とする。
　・従事者：登録番号を [会員].登録番号 → [相談員マスタ].相談員番号 の順に検索する。【要確認 D-16】
　・参照先（マスタ・親・従事者）が取得できない行は、その参照先を使うチェックを行わない。
4. チェック区分と実行順
　入力チェックは次の 2 区分とし、① → ② の順に行う（区分名は設計・実装上の分類で、画面・ログには表示しない。11/05 本人決定。旧称：第1類（前提チェック）・第2類（関連チェック））。
　(1) ① ファイル内チェック（区分 1）：対象ファイルの 1 行（キー重複はファイル内）だけで判定するチェック。全ファイル・全行・全チェックを行う（エラーがあっても次の行・ファイルのチェックを続ける）。
　(2) ② 整合性チェック（区分 2）：他のファイルの行 または 既存データ を参照するチェック。ファイル内チェックのエラーが 0 件の場合のみ、行を事業キーで事業ごとにまとめてから行う。全行・全チェックを行う。
　　整合性チェックは LWC と Apex の 2 つで行い、並行して実行する（Apex の呼出しを先に開始し、応答を待つ間に LWC のチェックを行う。11/09）。
　　・LWC：取込データの行どうしの関連（ファイル・行・事業をまたぐ検索）。他の事業の取込データとの重複（No.62・63・82・83 の取込データの部分）はエラーにする。同じ事業の行の関連（応募・明細・実績の有無、募集人数、割当の件数）は、既存データと合わせて判定する必要があるため、求めた値を Apex に渡す（6 章）。
　　・Apex：既存データ（DB）との関連（読み取りのみ）。取込データの関連は LWC が求めた値を使い、Apex の中では行どうしを検索しない。LWC から行を一定の行数で区切って複数回呼び出す（事業の途中で分かれる場合がある）【要確認 F-7】。検索条件は「32」■5 (2)。
　(3) ファイル内チェックで行わないチェック（原因のエラーのみ出力する）
　　・No.1・2 がエラー：以降のチェックを行わない。
　　・No.3・4 がエラー、またはファイルが読み込めない：そのファイルのチェックを行わない。
　　・列数が一致しない行（No.5）：その行の他のチェックを行わない。
　　・単項目（No.6～9）：1 項目につき No.6 → 7 → 8 → 9 の順に判定し、最初のエラーのみとする。
　　・相関・範囲チェック：参照する項目のいずれかが単項目でエラーの場合は行わない。
　　・キー重複（ファイル内）：キー項目が単項目でエラーの行は対象外。重複する行はすべてエラーとする。
　(4) 登録時のエラー（入力規則等）：その事業の登録を取り消す（「32」）。入力規則の条件は整合性チェックまでで網羅する（11/09 確認済み：入力規則は従事事業の 15 件のみ（E-8））。ただし 規則 9・13（内税・外税 必須）は CSV では任意のため、登録時に省略値（外税）を設定して満たす【要確認 D-56】。
5. エラー出力
　・ファイル単位のエラー（No.1～4、ファイルが読み込めない場合の No.5）：画面に表示する。No.3～5 は先頭に「登録対象：」を付ける。
　・行単位のエラー（ファイル内チェック・整合性チェック）：区分・登録対象・ファイル名・行番号・チェック No.・メッセージ ID・メッセージ を集め、当面はブラウザのコンソールログに出力し、画面には「対象ファイルにエラーが見つかりました。（SYSTEM-6105）」を表示する。【要確認 F-8】
　・ログの形式：「エラー n 件」の後、ファイル名ごとに「n行目_メッセージ」を行番号の順（同じ行は項目の順）に出力する。区分名は出力しない。
　・エラーがあった区分のエラーのみ出力して終了する（ファイル内チェックでエラーがあれば整合性チェックは行わない）。エラーが 1 件でもある場合は全ファイルとも登録しない。
　・エラー内容のポップアップ：行単位のエラーがある場合、チェック終了時に自動で表示する。閉じた後は画面の「エラー内容を表示」から再表示できる。
　　表示内容：「エラーが n 件見つかりました。」、登録していない旨（エラーログを確認し CSV を修正して再登録）、登録対象・ファイル名ごとのエラー件数。区分名・区分の説明は表示しない（11/05 リーダー）。
　　ボタン：「エラーログをダウンロード」（コンソールログと同じ内容をテキストファイルで保存し、ポップアップを閉じる）、「キャンセル」（閉じる）。
　・エラーログ：ファイル名「ファイル一括登録_エラーログ_YYYYMMDD_HHmmss.txt」、UTF-8（BOM 付き）・改行 CRLF。先頭に表題・出力日時、続けてログの形式で出力する。
　・エラーの消去：参照ボタンでファイルを選び直した場合（同じファイルの選び直しを含む）、画面のエラーメッセージとエラー内容（ポップアップ）を消す。前回の取込のエラーと区別するため（11/05 リーダー）。クリアボタンでも消す。
6. 整合性チェックの受け渡し（LWC ⇔ Apex）
　・メソッド：Juj_JigyoCsvUploaderController.checkCategory2(String requestJson) → { errors: List<CheckError> }
　・呼出し：行（6 ファイルの合計）を 2,000 行ずつに分け、順番に呼び出す（並列にしない）。行の多い事業は複数の呼出しに分かれる。【要確認 F-7】（11/09 変更：従来は 50 事業ずつ。1 事業の行が多い場合に 1 回の呼出しが大きくなるため）
　・リクエスト：{ jigyoList: [ { key, jigyoNo, basyoNo, nendo, hasCsvJigyo, hasCsvMeisai, csvJigyoFlags, rows: [ { fileKey, lineNo, data:{項目名→値}, csv～ } ] } ] }
　　rows はその呼出しに含まれる行のみ。同じ事業の他の行との関連は、LWC が事業の全行から求めて次の項目で渡す（Apex は呼出し内の行どうしで判定しない）
　　| 項目 | 内容 | チェック No. |
　　|---|---|---|
　　| hasCsvJigyo | 取込データに従事事業の行がある | 29 |
　　| hasCsvMeisai | 取込データに従事事業明細の行がある | 61・81 |
　　| csvJigyoFlags | 取込データの従事事業の応募時入力項目フラグ 8 項目（従事事業の行がない場合は null）| 42～47 |
　　| 行.csvHasOuboMeisai | 応募：同じ登録番号の応募明細がある | 43 |
　　| 行.csvHasOubo | 応募明細：同じ登録番号の応募がある | 51 |
　　| 行.csvHasMeisai | 応募明細・割当・実績：同じ日の従事事業明細がある | 52・61・81 |
　　| 行.csvFlaggedCount | 明細・割当：同じ日の 割当フラグ＝1 または 確定フラグ＝1 の割当の件数 | 36・64 |
　　| 行.csvBosyuNinzu | 割当：同じ日の従事事業明細の募集人数 | 64 |
　　| 行.csvHasJisseki | 割当：同じ登録番号・同じ日の実績がある | 65 |
　・エラー：{ fileKey, lineNo, checkNo, messageId, x, y, z }。メッセージの文言は LWC で作る。
　・Apex で例外が発生した場合：画面にその内容を表示し、登録しない。
　・実装：Juj_JigyoCsvCheckService。既存データはオブジェクトごとに IN 条件でまとめて取得する。エラーは同じ行ではチェック No. の順に出力する。
　・ユーザ種別・支部コードはリクエストで受け取らず、Apex で取得する（前提 2）。
　・親の従事事業がない行（No.29 エラー）は、そのファイルの以降のチェックを行わない。従事者が特定できない行（No.39・40・50・58・76 エラー）は、従事者を使うチェックを行わない。
